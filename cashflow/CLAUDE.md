# Правила работы над подсистемой cashflow

Учёт денег ИП: выписка Т-Бизнеса → схема `finance` в PostgreSQL → витрины → DataLens.
Владелец не программист, объясняй действия простыми словами до выполнения.

## Приоритеты, в этом порядке

Корректность денег → сохранность существующих данных → идемпотентность →
простота поддержки → красота кода.

## Чего нельзя делать никогда

- Трогать схемы магазина. `finance_sync` владеет только схемой `finance`;
  доступ к таблицам заказов выдаётся отдельно, только SELECT на конкретные
  колонки и только с явного согласия владельца.
- Добавлять в код методы платежей T-API. Токен — только «Счета и выписки».
- Угадывать статью операции. Не совпало с правилом — значит «Не разобрано».
  Молчаливая догадка искажает отчёт сильнее, чем честный пропуск.
- Писать токен, пароли и ФИО физлиц в логи, витрины, тесты и git.
- Менять `postgresql.conf`, `pg_hba.conf`, файрвол или группы безопасности
  без резервной копии файла и явного «да» от владельца.
- Запускать тесты, которые пишут в базу, против прода. Интеграционные тесты
  работают только с базой, в имени которой есть `test`.

## Как устроен код

- `engine.py` — правила классификации, чистая логика без базы. Сюда же тесты.
- `classify.py` — чтение справочников из базы и запись результата.
- `tbank.py` — клиент выписки: пагинация по курсору, ретраи на 429/5xx,
  терпимый разбор имён полей. **При расхождении с документацией T-API
  приоритет у документации** — правь `_pick`/`parse_operation`, а не подгоняй ожидания.
- `importer.py` — загрузка CSV с валидацией по принципу «всё или ничего».
- `migrations/` — пронумерованные SQL-файлы, каждый записывает себя
  в `finance.schema_migrations`. Миграции не переписываются задним числом,
  изменения добавляются новым файлом.

## Деньги

- Суммы — `numeric(18,2)` в базе и `Decimal` в Python. Никаких float.
- В `raw_operations` и `fact_operations` есть `amount` (всегда положительная)
  и вычисляемая `amount_signed` (расход со знаком минус). Суммировать нужно
  `amount_signed` — тогда сумма за период сразу даёт изменение остатка.
- Остатки никогда не суммируются между периодами: берутся из `v_daily_balance`
  на конкретный день.
- Нет данных об остатках — витрина показывает `NULL`, а не ноль.
  Ложное расхождение хуже отсутствия цифры.
- Платёж по кредиту делится по `loan_schedule` на две строки `fact_operations`
  с разными `split_no`. Сумма частей обязана совпадать с платежом до копейки.

## Обязательные свойства, которые проверяются тестами

- `check_diff = 0` в каждом месяце.
- Потоки за квартал и год равны сумме месячных.
- Повторный `sync` и повторный `classify` не меняют ни количество строк, ни суммы.
- Контрагенты-физлица в витринах замаскированы.
- `datalens_ro` читает только пять витрин и ничего больше.

Меняешь витрины или классификацию — прогоняй `tests/test_integration_db.py`
против тестовой базы, а не только юнит-тесты.

## Как добавить новую статью

1. Строка в `data/articles.csv` (и в правила, если нужно автоматическое отнесение).
2. Если статья участвует в расчёте FCF, FCFE, DSCR или долей — обнови `v_flows`
   и `v_metrics` новой миграцией.
3. Добавь тест, фиксирующий поведение.

Идентификаторы статей (`cff_loan_principal`, `cfo_out_loan_interest`,
`tech_loan_payment`, `tech_unclassified`) зашиты и в SQL витрин, и в `engine.py`.
Переименование — это миграция плюс правка кода, не что-то одно.
