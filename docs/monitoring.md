# Мониторинг, алерты и ежедневный отчёт

Что ломается — узнаём из Telegram-чата **Ops**, а не от клиента. Два
источника сообщений:

- **алерты** шлёт Yandex Monitoring своим ботом `@YandexCloudNotify_bot`.
  Он работает, даже если наш контейнер лежит целиком — в этом и смысл;
- **ежедневный отчёт** в 09:00 по Москве шлёт сам бот, тиком расписания.

Срочные одиночные события («СДЭК отказал по оплаченному заказу» и т.п.)
по-прежнему уходят менеджеру сразу из кода. Алерты их не заменяют, а
страхуют: если сломается сам механизм уведомлений, счётчик ошибок всё
равно поднимется.

## Как устроено

```
клиент ─ ВК ─> очередь ─> контейнер ──┬─> ЮKassa / СДЭК / Ozon / Claude
                                      │      (обёртка journal.watch: сбой → буфер)
                                      ├─> ответ клиенту (замер → буфер)
                                      └─> буфер → таблица ops_events (после запроса)

таймер «ops-pulse» раз в минуту ─> контейнер: проверка базы, окно 10 мин
   из ops_events → метрики → Monitoring API ─> алерты ─> @YandexCloudNotify_bot ─> Ops

ВМ с базой ─> Unified Agent ─> метрики диска ─> алерт «диск»
           ─> гипервизор ─> метрики Compute ─> алерт «ВМ недоступна»
```

Почему через базу, а не сразу в Monitoring: экземпляров контейнера может
быть несколько, и p95 по всем ответам честно считается только там, где они
собраны вместе. Заодно мониторинг не стоит на пути ответа клиенту: запись в
буфер ничего не стоит, а сбой базы или Monitoring только теряет точку.

Код: `app/modules/ops/` (журнал, пульс, отчёт, клиент Monitoring),
`app/core/logs.py` (JSON-логи и маскировка).

## Метрики

Все — `DGAUGE`, пишутся раз в минуту пульсом, `service=custom` в каталоге бота.

| Метрика | Метки | Что значит |
|---|---|---|
| `bot_heartbeat` | — | 1, если пульс дошёл. Нет точек — бот не работает |
| `bot_db_up` | — | 1/0: ответила ли база контейнеру |
| `bot_turns` | — | сколько ответов клиентам за 10 мин |
| `bot_response_p95_seconds` | `stage=total\|llm` | p95 ожидания ответа за 10 мин; `llm` — доля Claude |
| `bot_response_p50_seconds` | `stage=total\|llm` | то же, медиана |
| `external_api_errors` | `api=yookassa\|cdek\|ozon\|claude` | сбои сервиса за 10 мин, без `validation` |
| `external_api_validation` | `api=…` | отказы из-за ввода клиента — на дашборд, не в алерт |

«Ответ клиенту» — от времени сообщения клиента (по часам ВК) до успешной
отправки ответа в ВК. В него входит и склейка сообщений (до 4 секунд).
Задержки в окне нет, если не было ответов: тогда p95 не отправляется.

Виды сбоев (`error_kind` в журнале, `error_code` в логе): `timeout`,
`network`, `auth` (401/403), `http_4xx`, `http_5xx`, `validation`
(опечатка в городе, тариф не найден, Ozon отказал в расчёте по пункту),
`other`. Что куда относится — `journal.classify`.

Что считается сбоем сервиса:

- **ЮKassa** — любой запрос к API (`_call`) и разбор уведомления о платеже;
- **СДЭК** — расчёт тарифов, полный расчёт, пункты города, создание заказа,
  статус заказа; истёкший токен приходит как `auth`;
- **Ozon** — любой запрос к API (`call`, в том числе выгрузка пунктов),
  расчёт (`checkout`), создание отправления;
- **Claude** — ход диалога, мини-отчёт, ответ без инструментов.

Вложенные вызовы считаются один раз: сбой СДЭКа внутри обработки
уведомления ЮKassa — это сбой СДЭКа, не ЮKassa.

## Алерты

Создаются в консоли: Monitoring → Алерты → Создать. Во всех — канал **Ops
Telegram** (см. «Настройка», шаг 6), статусы `Alarm`, `Warning`, `No data`,
`OK`, повторная отправка — **раз в час** (на `OK` повтор не действует).

Окно у счётчиков короткое (2 мин), потому что 10-минутное окно уже
посчитал пульс: алерт смотрит на последнее значение.

| # | Алерт | Запрос | Условие | Окно | Нет данных |
|---|---|---|---|---|---|
| 1 | ВМ с базой недоступна | метрика Compute `cpu_utilization` ВМ `epd61hgvour5kh6dc2tg` (имя метрики сверить в обозревателе: Compute Cloud → ВМ) | Количество < 1 → Alarm | 3 мин | **Alarm** |
| 1б | База не отвечает боту | `bot_db_up` | Последнее < 1 → Alarm | 3 мин | OK (это ловит №2) |
| 2 | Бот не работает | `bot_heartbeat` | Количество < 1 → Alarm | 3 мин | **Alarm** |
| 3 | Медленный ответ | `bot_response_p95_seconds{stage="total"}` | Последнее > 30 → Warning, > 60 → Alarm | 2 мин | OK |
| 4 | Диск ВМ заполнен | метрика заполненности `/` от Unified Agent (имя — после установки агента) | Последнее > 80 → Warning, > 90 → Alarm | 5 мин | Warning |
| 5 | Ошибки ЮKassa | `external_api_errors{api="yookassa"}` | Последнее > 0 → Warning, > 2 → Alarm | 2 мин | OK |
| 6 | Ошибки СДЭК | `external_api_errors{api="cdek"}` | то же | 2 мин | OK |
| 7 | Ошибки Ozon | `external_api_errors{api="ozon"}` | то же | 2 мин | OK |
| 8 | Ошибки Claude | `external_api_errors{api="claude"}` | Последнее > 2 → Alarm | 2 мин | OK |

«> 0» и «> 2» — это «≥ 1» и «≥ 3» из задания: значения целые.

Для 3 и 5–8 «нет данных» — OK намеренно: когда пульса нет, звонит алерт 2,
и дублировать его пятью сообщениями незачем.

### Пороги

- **пороги алертов** — в самих алертах, в консоли: «Редактировать» →
  условия. Код менять не нужно;
- **окно 10 минут**, час отчёта, срок хранения журнала — переменные
  окружения `OPS_WINDOW_MINUTES`, `OPS_REPORT_HOUR_MSK`,
  `OPS_EVENTS_KEEP_DAYS` (по умолчанию в `app/core/config.py`);
- **что считать опечаткой клиента** — `_VALIDATION_MARKERS` в
  `app/modules/ops/journal.py`.

### Заглушить на время работ

На странице алерта — «Деактивировать», после работ — «Активировать».
Перед плановыми работами на ВМ с базой гасить алерты 1, 1б и 2.

## Runbook

**1. ВМ с базой недоступна.** Консоль → Compute Cloud → ВМ: статус
`RUNNING`? Если `STOPPED` — запустить (проверить, не остановил ли кто-то
намеренно). Если `RUNNING`, а метрик нет — подключиться по ssh, `uptime`,
`docker ps` (жив ли `teashop-postgres`). Бот при недоступной базе не падает,
но живёт в памяти: после восстановления проверить `scripts/api.sh health`.

**1б. База не отвечает боту.** `scripts/api.sh health` → `database`. На ВМ:
`docker ps`, `docker logs --tail 50 teashop-postgres`. Таймаут — фильтр
(группа безопасности), «connection refused» — Postgres не запущен
(`docs/infrastructure.md`, «Диагностика»).

**2. Бот не работает.** `scripts/api.sh health`: отвечает? Консоль →
Cloud Functions → Триггеры → `ops-pulse` активен? Консоль → Serverless
Containers → `tea-shop-vk-bot` → Логи за последние минуты: ошибки старта,
`forbidden` (токен в поле «Данные» триггера не совпал). Ревизия упала —
Actions → Run workflow.

**3. Медленный ответ.** Дашборд: растёт `stage=llm` — тормозит Claude,
ждать или смотреть статус Anthropic; растёт только `total` — тормозит наш
код или перевозчики: в логах строки `ход peer_id=… claude=… инструменты=…`.

**4. Диск.** На ВМ: `df -h`, `sudo du -sh /var/log/journal /var/backups/*`,
`sudo journalctl --vacuum-size=200M`. База растёт — `pg_wal` и
`ozon_delivery_points`. Диск 10 ГБ: увеличить можно в консоли без
пересоздания ВМ.

**5–8. Ошибки сервиса.** Cloud Logging, запрос
`json_payload.service = "cdek"` (или `yookassa`, `ozon`, `claude`):
`error_code` и `http_status` скажут, что именно. `auth` — истёк или сменился
ключ (секрет в GitHub → передеплой); `http_5xx`/`timeout` — сбой у
сервиса, проверить их статус и подождать; номер заказа — в `order_id`,
по нему видно, кого задело.

## Логи

Консоль → Cloud Logging → лог-группа `default` (или Serverless Containers →
`tea-shop-vk-bot` → Логи). Каждая запись — JSON: `ts`, `level`, `message` и
для сбоев `service`, `operation`, `order_id`, `http_status`, `error_code`,
`duration_ms`. Примеры запросов:

```
json_payload.service = "cdek"
json_payload.error_code = "auth"
level = ERROR
```

Срок хранения группы сейчас **3 дня**. Задание просит 7–14; продлевать —
после оценки объёма (Cloud Logging → группа → объём за сутки).

**Персональных данных в логах нет:** форматтер заменяет телефоны, почты,
токены и пароли в адресах заглушками, а код не пишет ФИО, адреса и текст
переписки вовсе. Имена и адреса регуляркой не ловятся — поэтому правило для
кода: в лог только идентификаторы (`peer_id`, `order_id`, код пункта).

## Ежедневный отчёт

Тик расписания после 09:00 МСК, раз в сутки, в `TELEGRAM_OPS_CHAT_ID`:
аптайм (доля минут с пульсом), p50/p95 ответа и доля Claude, число
диалогов, сбои по сервисам (и отдельно — ввод клиентов), заполненность
диска, время последних задач по расписанию: тик бота, отчёт о
недоставленном, выписка Т-Банка и бэкап `finance` (после шага 5
настройки). Задача, которая молчит дольше обычного, помечена ⚠️.

Прислать сейчас, без отметки «отправлен»: `scripts/api.sh ops/report`.

## Проверка алертов

Ничего на боевом не ломаем — эмулируем:

| Что | Как | Ждём |
|---|---|---|
| 2, бот не работает | Триггер `ops-pulse` → «Остановить» на 5 мин, потом «Запустить» | Alarm через ~3 мин, OK после запуска |
| 3, медленный ответ | `scripts/api.sh 'ops/emulate?latency=45&count=5'`, затем `latency=90` | Warning, затем Alarm; OK через ~10 мин |
| 4, диск | временно снизить порог Warning до текущего значения − 1 | Warning; вернуть порог |
| 5–8, сбои | `scripts/api.sh 'ops/emulate?api=cdek&count=3&kind=http_5xx'` (вид: `http_5xx`, `http_4xx`, `auth`) | Alarm; OK через ~10 мин |
| 1, ВМ | только с согласия владельца: короткая остановка ночью, или тестовый алерт с тем же запросом и порогом, который заведомо срабатывает | Alarm |
| отчёт | `scripts/api.sh ops/report` | текст в Ops |

Эмуляция пишет в журнал записи с операцией «эмуляция»: пульс их считает,
ежедневный отчёт — нет. Внешние сервисы при этом не вызываются.

## Настройка (один раз, каждый шаг — с подтверждением владельца)

1. **Ops-чат**: группа в Telegram, в ней наш бот (тот же, что пишет
   менеджеру) и `@YandexCloudNotify_bot`. `chat_id` группы — в секрет
   GitHub `TELEGRAM_OPS_CHAT_ID`.
2. **Роль** `monitoring.editor` сервисному аккаунту `teapot-twice-ai` (им
   контейнер пишет метрики). Роли «только запись» у Monitoring нет.
3. **Деплой** этой версии (Actions или мерж в `main`).
4. **Триггер** `ops-pulse`: Cloud Functions → Триггеры → Создать, тип
   «Таймер», cron `* * ? * * *` (раз в минуту), приёмник — контейнер
   `tea-shop-vk-bot`, сервисный аккаунт `teapot-twice-ai`, в поле
   «Данные» — `ops-pulse <INTERNAL_API_TOKEN>`. **Это четвёртое место, где
   живёт токен.**
5. **ВМ с базой** (с резервной копией и подтверждением):
   - отдельный сервисный аккаунт только с `monitoring.editor` — вместо
     `teapot-twice-ai`, который сейчас привязан к ВМ и даёт с неё право
     деплоить контейнер. Перед заменой — проверить, что на ВМ никто не
     берёт токен из метаданных;
   - Unified Agent: диск, память, CPU раз в минуту;
   - отметки задач `cashflow` и `cashflow-backup`: файлы из `ops/vm/`
     (нужен systemd ≥ 249 для `OnSuccess=`, проверить `systemctl --version`).
6. **Канал** в Monitoring: Каналы уведомлений → Создать, способ Telegram,
   получатель — группа Ops.
7. **Алерты** по таблице выше и **дашборд**: виджеты `bot_heartbeat`,
   `bot_response_p95_seconds` (обе стадии), `external_api_errors` по
   `api`, заполненность диска, `bot_db_up`.
8. **Проверка** по таблице «Проверка алертов».

## Стоимость в месяц

| Что | Объём | Цена |
|---|---|---|
| Метрики пульса | ~14 значений в минуту ≈ 0,6 млн | 0,32 ₽ за млн → ≈ 0,2 ₽ |
| Unified Agent (узкий набор) | ≈ 1 млн | ≈ 0,3 ₽ |
| Чтение метрики диска для отчёта | 1 запрос в сутки | копейки |
| Вызовы контейнера пульсом | 43 200, ~0,1–0,2 с | в бесплатном лимите (1 млн вызовов); сверх него ≤ 10–18 ₽ |
| Алерты, канал, дашборд | — | не тарифицируются |
| Таблица `ops_events` | ~45 тыс. строк за 30 дней | место на диске ВМ, несколько МБ |

Итого — около 1–20 ₽ в месяц. Объём логов не меняется заметно: JSON
длиннее текста на десятки байт на строку.

## Где задание разошлось с документацией Yandex Cloud

- перцентилей у алертов нет — p95 считает пульс и пишет готовым числом;
- метрики-счётчика с окном в алерте не нужно — пульс пишет число сбоев за
  10 минут, алерт смотрит последнее значение;
- метка `service` в пользовательских метриках занята (`service=custom`),
  поэтому сервис — в метке `api`;
- нативный Telegram-канал есть, но пишет бот Яндекса своим текстом; наш
  текст («Заказы: #1042, ссылка на логи») возможен только через Cloud
  Function, а Telegram из облака доступен лишь через наш прокси;
- роли «только запись метрик» нет — минимальная `monitoring.editor`;
- у бота нет ВМ и цикла Long Poll: это Serverless Container, пульс — от
  минутного таймера; systemd-таймера для отчёта нет — его шлёт тик бота.
